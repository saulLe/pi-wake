# Pi 二次开发可行性分析

> 结论：完全可行，且 Pi 的架构本身就是为二次开发设计的。大多数情况下不需要 fork 源码，选对层级能省掉 80% 工作量。

## 为什么可行

| 设计 | 对二开的意义 |
|---|---|
| 7 个 npm 包拆分发 | 可只消费 `@earendil-works/pi-ai` 或 `pi-agent-core`，不用整包吃下 |
| 扩展是 TypeScript 模块 | 能注册工具、斜杠命令、快捷键、事件钩子、UI，甚至自定义 provider |
| 官方"让 Pi 改自己" | 直接对话让 Pi 写扩展 → `/reload` 生效，有 50+ 官方示例 |
| MIT 协议 | 商用、闭源分发都没问题 |

## 四条路径（按投入与掌控力递增）

详见 `架构图-二开路径.svg`。

| 路径 | 做什么 | 工作量 | 适合场景 | 风险 |
|---|---|---|---|---|
| 装包 / Skill | 给 Pi 加领域知识（如 Velocity/SQL 规范） | 极低（零代码，分钟级） | 复用现成能力 | 无 |
| 写 Extension | 定制工具、命令、上下文注入、权限钩子 | 低～中 | 定制工具与命令 | API 可能随版本变 |
| SDK / RPC 嵌入 | 把 agent 能力嵌进自己的系统 | 中 | 嵌入自有应用 | 要自己管会话与权限边界 |
| Fork 内核 | 改 agent 循环、上下文组装逻辑 | 高 | 深度改造内核 | 升级合并痛苦、需跟版本 |

## 结合本项目的建议

- 想让 Pi 懂 Velocity 模板 + SQL 表结构规范 → 走 **Skill + 轻量 Extension**，不用碰源码。
  把代码规范、表关联约定写成 `AGENTS.md` / Skill，让 Pi 按规则改代码，比改它本身划算。
- 想塞进行情监控系统当自动分析执行层 → 走 **RPC / SDK** 更合适。

## 需要提前知道的坑

1. **项目年轻**：2025 年 8 月建仓，版本迭代快，扩展 API 有 breaking change 风险，锁版本 + 看 changelog 是必须的。
2. **没有内置权限系统**：默认以启动用户权限跑，给其他人用或跑不可信代码必须自己加沙箱（官方给了 Docker / Gondolin / OpenShell 三种方案）。
3. **省略的功能要自己补**：sub-agent、plan mode、权限弹窗、后台任务都没有，得装包或让 Pi 现写。
4. **Node.js ≥ 22.19**：环境要跟上；本地安装时 `@earendil-works/p3` 要求 Node ≥ 26.3.1（属 apps/p2 实验模块，不影响主 CLI）。

## 起步建议

从最小机制开始，够用即可，逐级升级：

| 需求 | 起点 |
|---|---|
| 给某目录持久指令 | AGENTS.md |
| 复用一个提示 | Prompt template |
| 任务专用的指令 + 支撑文件 | Skill |
| 可执行工具、命令、事件处理 | Extension |
| 自定义终端组件 | Terminal UI |
| 接不支持的模型服务 | Custom provider |
| 安装/分发多个资源 | Pi package |
