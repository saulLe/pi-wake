# 数字员工功能规划

> 结论先行：数字员工不做“玩具聊天机器人”，而是把 Pi 的能力组织成一个**可管理、可协作、可审计的本地虚拟公司**。每个员工有身份、岗位、模型、技能、记忆和权限；员工之间按公司协作方式通过**结构化消息 + 任务工单**沟通；用户是老板/管理员，可旁观、插话、审批和接管。

## 1. 定位与边界

| 项 | 说明 |
|---|---|
| 产品定位 | Pi Admin 内的一个一级模块，把“单个 AI 助手”升级为“多个角色分工协作的本地团队” |
| 核心价值 | 复杂任务拆给不同岗位并行处理，过程可见、结果可追溯，而不是一个模型从头聊到尾 |
| 技术边界 | 不修改 Pi 上游源码；通过配置、会话、进程/SDK 调度实现；所有数据留在本地 |
| 用户角色 | 老板（你）：建团队、下目标、看汇报、审批高风险动作、随时接管 |
| 员工角色 | 按岗位执行任务、向主管汇报、向同事提问、交接产物，不能越过权限边界 |
| 第一版边界 | 先做**组织与沟通闭环**（配置 + 消息 + 任务），再接真实执行引擎；每个阶段都可独立演示，不留半成品 |

## 2. 核心概念

| 概念 | 定义 | 对应到公司 |
|---|---|---|
| 员工 Employee | 一个可独立运行的 AI 实例：身份 + 模型 + 技能 + 记忆 + 权限 + 工作区 | 一名具体员工 |
| 岗位 Role | 可复用的职责模板，决定默认技能、提示词、权限和输出格式 | 职位（产品经理、开发、测试） |
| 部门 Department | 员工的分组，带负责人和职责边界 | 部门 / 小组 |
| 汇报线 Reporting | 员工之间的上级关系，决定任务分派和汇报路径 | 组织架构 |
| 任务 Task | 最小工作单元，有输入、验收标准、依赖、负责人和状态 | 工单 / 项目任务 |
| 消息 Message | 员工之间、人与员工之间的结构化沟通记录 | 邮件 / IM / 会议纪要 |
| 频道 Channel | 按部门、项目或任务建立的沟通空间 | 群聊 / 会议室 |
| 产物 Artifact | 任务输出的文件、代码片段、报告或结论 | 交付物 |
| 记忆 Memory | 员工长期记忆 + 任务短期上下文 + 组织共享知识 | 工作笔记 / 公司知识库 |

## 3. 默认岗位模板

创建员工时先选岗位，再覆盖参数。岗位模板让“像公司一样”这件事开箱即用。

| 岗位 | 主要职责 | 默认技能/工具 | 默认权限 | 典型输出 |
|---|---|---|---|---|
| 主管 / Lead | 拆目标、分任务、汇总汇报 | 任务规划、摘要 | 只读全局 + 任务分派 | 任务拆解、里程碑、汇总报告 |
| 产品经理 | 需求澄清、写规格、验收 | 文档、检索 | 只读代码 + 写文档区 | PRD、验收清单 |
| 架构师 | 技术方案、接口边界、评审 | 代码检索、设计文档 | 只读代码 + 写设计区 | 技术方案、评审意见 |
| 开发工程师 | 编码、重构、调试 | Pi coding agent、代码库 | 限定工作区写权限 | 代码改动、提交说明 |
| 测试工程师 | 用例设计、回归、缺陷报告 | 测试命令、日志检索 | 只读 + 测试目录写 | 测试报告、缺陷清单 |
| 运维工程师 | 环境、部署、监控 | 部署脚本、日志 | 命令执行（需审批） | 部署记录、巡检报告 |
| 数据分析师 | 查数、指标、可视化 | SQL skill、表格 | 数据源只读 + 报告区写 | 分析结论、图表 |
| 秘书 / 协调员 | 会议纪要、进度追踪、提醒 | 消息汇总、日历 | 仅消息与任务权限 | 日报、周报、待办提醒 |

岗位可自定义：复制模板后修改提示词、技能、权限和输出格式，不影响内置模板。

## 4. 沟通与协作机制（重点）

### 4.1 三种沟通形态

| 形态 | 场景 | 实现方式 |
|---|---|---|
| 私聊 Direct | 一员工向另一员工提问、交接任务 | `to` 指定单个员工 ID |
| 频道 Channel | 部门例聊、项目群同步 | `channel` 指定频道，成员可见 |
| 广播 Broadcast | 主管发全员通知、紧急暂停 | `type=broadcast`，由调度器展开为收件箱 |

### 4.2 消息类型（结构化协议）

员工之间不是自由闲聊，而是发“带语义的消息卡片”。这样可追溯、可执行、可审计。

| type | 含义 | 典型字段 |
|---|---|---|
| `task_assign` | 主管派活 | `taskId`, `assignee`, `deadline`, `acceptance` |
| `task_accept` | 接单确认 | `taskId`, `eta` |
| `status_report` | 进度汇报 | `taskId`, `progress`, `blocker` |
| `question` | 向同事/主管提问 | `taskId`, `replyTo`, `question` |
| `answer` | 回答 | `replyTo`, `answer`, `sources` |
| `handoff` | 产物交接 | `taskId`, `to`, `artifacts[]` |
| `review` | 评审请求/结论 | `taskId`, `verdict`, `comments` |
| `broadcast` | 广播通知 | `scope`, `body` |
| `escalation` | 升级/求助 | `taskId`, `reason`, `needsApproval` |

消息信封：

```json
{
  "id": "msg_20261126_001",
  "channel": "project-pi-admin",
  "from": "lead-01",
  "to": "dev-01",
  "type": "task_assign",
  "taskId": "task_014",
  "replyTo": null,
  "body": "实现员工列表页，验收标准见任务卡",
  "artifacts": [],
  "createdAt": "2026-11-26T14:00:00+08:00"
}
```

### 4.3 一次完整协作的流程

1. 用户给主管一个目标：“做一个数字员工管理界面”。
2. 主管拆解成任务卡：需求规格、UI 设计、后端 API、测试，分别派给产品经理、架构师、开发、测试。
3. 产品经理在频道发规格，架构师基于规格回技术方案，开发接任务后提问，主管回答。
4. 开发完成把代码/截图作为 `artifacts` 通过 `handoff` 交给测试。
5. 测试发 `review`；不通过则回退并附缺陷清单，通过则主管汇总 `status_report` 给用户。
6. 全程消息进入公共时间线，用户可在任意节点插话、改派、审批或叫停。

### 4.4 上下文与记忆隔离

- 每个员工有独立 Pi 会话，避免把 A 的对话塞进 B 的上下文。
- 员工之间只传递**消息摘要 + 任务卡 + 产物路径**，不直接共享完整聊天记录。
- 部门频道保留公共上下文；任务结束写“任务纪要”到组织知识库。
- 长期记忆按员工分文件，支持用户手动编辑和清理。

### 4.5 调度与防失控

| 机制 | 规则 |
|---|---|
| 任务队列 | 状态机：`todo → assigned → doing → review → done/blocked/cancelled` |
| 并发上限 | 全局和每员工可设并行任务数，默认 1，防止成本爆炸 |
| 轮次上限 | 一次任务内员工互相追问最多 N 轮，超出自动升级给用户 |
| 超时与重试 | 任务超时转 `blocked`，可重试或改派，不静默失败 |
| 预算上限 | 每员工/每任务设 token 与费用上限，触顶暂停并汇报 |
| 人类审批 | 删除文件、执行命令、网络外发、花钱超过阈值需用户确认 |

## 5. 数据模型与目录

所有数据放在工作区内，不写 Pi 上游源码：

```
my-workspace/org/
├── organization.json          # 组织名、部门、汇报线、全局策略
├── departments.json           # 部门定义与负责人
├── employees/
│   ├── lead-01.json           # 单个员工的完整配置
│   └── dev-01.json
├── roles/
│   └── templates.json         # 岗位模板（内置只读 + 用户自定义）
├── tasks/
│   └── task_014.json          # 任务卡
├── messages/
│   ├── project-pi-admin.jsonl # 频道消息（追加写）
│   └── dm-lead-dev.jsonl      # 私聊消息
├── memory/
│   └── dev-01/
│       └── notes.md           # 员工长期记忆
├── artifacts/                 # 任务产物（报告、截图、代码片段）
└── runs/
    └── run_20261126_001/      # 一次执行的日志与状态快照
```

员工配置示例：

## 6. API 设计

沿用现有 `server.mjs` 的约定：默认只读、写操作需 `unlocked`、写前自动备份、路径白名单、密钥脱敏。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/org/overview` | 组织统计：人数、在线、任务、费用 |
| GET/POST | `/api/org/employees` | 员工列表 / 创建 |
| GET/PUT/DELETE | `/api/org/employees/:id` | 员工详情 / 更新 / 归档 |
| POST | `/api/org/employees/:id/toggle` | 上线 / 停用员工 |
| GET/POST | `/api/org/departments` | 部门列表 / 创建 |
| GET/POST | `/api/org/roles` | 岗位模板列表 / 自定义模板 |
| GET/POST | `/api/org/tasks` | 任务列表 / 建任务 |
| POST | `/api/org/tasks/:id/assign` | 分派 / 改派 |
| POST | `/api/org/tasks/:id/transition` | 状态流转 |
| GET | `/api/org/messages?channel=&since=` | 拉取消息 |
| POST | `/api/org/messages` | 发送消息（人或员工） |
| GET | `/api/org/events` | SSE 实时推送消息与任务变化 |
| POST | `/api/org/run` | 启动一次任务执行（接 Pi 引擎阶段启用） |
| GET | `/api/org/artifacts/:id` | 查看任务产物 |

## 7. 界面设计

侧栏新增分组「数字员工」，与现有专业版风格完全一致（同一套图标、卡片、主题、空状态、骨架屏、命令面板）。

| 页面 | 布局 | 关键交互 |
|---|---|---|
| 组织概览 | 组织架构树 + 状态卡 + 今日动态 | 点员工进详情；点部门过滤 |
| 员工管理 | 卡片/表格 + 筛选搜索 | 创建向导（身份→岗位→模型→技能→权限→记忆）、启停、克隆、归档 |
| 任务看板 | 四列看板：待办/进行中/待审核/完成 | 拖拽改派、点卡片看消息与产物、设验收标准 |
| 沟通中心 | 左：频道与私聊；中：消息流；右：任务上下文 | @提及、消息卡片点击跳任务、审批卡片、人工插话 |
| 知识库（后续） | 文档列表 + 检索 | 查看任务纪要、编辑员工记忆、共享知识 |

创建员工向导是体验重点：选岗位后自动带出模型建议、技能、权限和输出格式，用户只改差异项；全程可返回，不强制一次填完。

深链与命令面板同步扩展：`#employees`、`#tasks`、`#messages`、`#addemployee`、`#messages:project-pi-admin`。

## 8. 安全与治理

| 风险 | 控制措施 |
|---|---|
| 员工越权改文件 | 文件系统权限分 `none/read-only/workspace-write`，路径限制在自身工作区 + 共享区 |
| 密钥泄露 | 员工配置不返回明文 Key，统一引用模型与认证里的凭证 ID |
| 无限循环对话 | 轮次上限 + 超时 + 升级给人 |
| 费用失控 | 每任务/每员工 token 与费用上限，触顶自动暂停 |
| 危险操作 | 删除、命令执行、网络外发进审批队列，需用户点确认 |
| 行为不可追溯 | 消息、任务流转、工具调用全部追加写 JSONL，可回放 |
| 配置被写坏 | 写前备份到 `admin/.backups/`，支持一键回滚 |
| 模型/接口变化 | 员工只存引用，不复制凭证；模型页改一处全员生效 |

## 9. 分阶段路线图

每个阶段都交付**可演示的完整闭环**，不做“看起来快完成了但不能点”的半成品。

| 阶段 | 范围 | 交付物 | 验收标准 |
|---|---|---|---|
| P0 规划 | 产品定义、数据模型、API/UI 方案 | 本文档 + 架构图 | 你确认概念与协作流程 |
| P1 组织管理（已完成） | 部门管理、内置岗位模板、员工 CRUD、组织架构图、创建向导 | `admin/` 内组织概览 + 员工管理页面 | 已验证：建人/改人/启停/归档/部门保存、刷新持久化、写前备份、深浅主题正常 |
| P2 沟通闭环（已完成） | 消息总线、频道、任务看板、状态流转、团队 Group、群派活拆子任务 | 任务看板 + 协作中心 + 团队页面 | 能派活、汇报、交接、汇总，消息 JSONL 可追溯；群派活自动拆子任务 |
| P3 真实执行（已完成） | 接 Pi RPC 执行引擎，结果回写，SSE 实时进度，超时/中止保护 | 任务「调用 Pi 执行」+ 自主工作调度器 | 已验证：任务从下达→真实 DeepSeek 流式执行→结果回写→转待验收全程跑通 |
| P4 组织智能（部分完成） | 长期记忆 CRUD、组织知识库、权限红线、审批队列 | 员工工作台记忆/技能/权限页 + 知识库页 | 记忆/知识注入执行上下文；审批队列 API 就绪。待做：IM 接入、WakerFlow 多阶段编排、记忆自动沉淀与防腐 |

## 10. 与现有模块的关系

| 现有模块 | 复用方式 |
|---|---|
| 模型与认证 | 员工选模型直接引用这里的 Provider/Key，不另存凭证 |
| 资源管理 | 员工的技能/扩展从这里勾选，启停状态一致 |
| 会话中心 | 员工执行记录归档为 Pi 会话，可在会话中心回看 |
| 设置编辑 | 组织级策略（并发、预算、审批）作为新增配置项 |
| 主题与命令面板 | 数字员工页面沿用同一套主题变量与快捷操作 |

## 11. 已知取舍

- 第一版先做**配置与协作链路**，真实执行放到 P3，避免一上来就把不稳定因素混进产品体验。
- 多员工并发会显著增加 token 消耗，默认严格限流，由用户主动放开。
- 员工“像公司一样沟通”体现在**结构化协议和任务上下文传递**，不是让模型自由群聊；自由聊天容易产生不可追溯的幻觉。
- 不碰 Pi 上游源码，保证上游升级时本工作区可平滑跟随。
